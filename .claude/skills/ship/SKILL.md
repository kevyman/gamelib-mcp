# Ship a branch

One reviewer from another model family, once. The value is the blind spots a
different training distribution sees; the cost of a second pass is mostly
plausible-but-wrong findings that still have to be refuted. Rationale and
sources: `docs/patterns/review-and-merge.md`. Codex reads `AGENTS.md`
("Code Review Rules") — that file, not the PR comment, is where review
standards live.

## 0. Preconditions

- The branch is pushed and rebased on / merged with current `main`.
- The diff is one reviewable change. Above roughly 600 changed lines or more
  than one theme, split it first: a single review pass over a sprawling diff
  is where a second model adds least.
- Attribution rule: every comment, reply or review you post on GitHub ends
  with the Claude Code footer (`---` then `_Generated by [Claude Code](https://claude.ai/code)_`).

## 1. Preflight — spend the cheap reviewer first

1. Gates, exactly as CI runs them: `ruff check gamelib_mcp tests scripts`,
   `mypy gamelib_mcp`, `python -m pytest -q`.
2. `/code-review` (medium effort) on the diff — same family as the author,
   so it finds the obvious; fix those now so Codex's single pass is spent on
   what this family misses. If the diff touches `auth.py`, `http_admin.py`,
   `session_ingest.py`, the session-file save path (`_write_private_json` and
   the `set_*_session` functions, wherever they live), `data/steam_session.py`,
   `data/nintendo_pctl.py`, `data/db/readonly.py`, any webhook or outbound
   notifier, or anything with `subprocess`, also run `/security-review`.
3. Re-run the gates after fixes. Commit; push.

## 2. Open the PR

- Title = the squash subject (imperative, ≤ 72 chars, no trailing period).
- Body = `.github/pull_request_template.md` filled in — the "Why" and "What
  changed" sections become the squash commit message, so write them as the
  history you want. Fill "Review scope for Codex" honestly: it steers the one
  pass toward the risk.
- Open the PR READY (`create_pull_request` with `draft: false`) — the
  branch already passed the gates in step 1, so a draft protects nothing,
  and "opens a new PR for review" is the documented automatic trigger.
  Codex reacts 👀 within a minute when it picks the PR up. Do NOT comment
  `@codex review` up front: with automatic reviews on, that is two reviews,
  which is the thing this process exists to avoid. Post the comment only
  if nothing has happened after 10 minutes.
- If the automatic review does not start, the first thing to check is the
  repository's **Automatic reviews** toggle at
  https://chatgpt.com/codex/settings/code-review — it was off for this
  repo until 2026-09-02, which is why #162, #166 (draft → ready) and #167
  (opened ready) all needed the comment. The comment works regardless of
  the toggle.

## 3. Subscribe and wait

- `subscribe_pr_activity(owner, repo, pullNumber)`; schedule a `send_later`
  check-in ~20 minutes out in case the event is missed; end the turn.
- Do not poll with sleeps. Do not touch the branch while the review runs —
  a new push invalidates the reviewed commit.

## 4. Act on the review — one pass

For every Codex finding, in the thread:

1. **Reproduce or refute.** Write the test that demonstrates the finding.
   If it fails, keep it and fix the code. If it cannot be made to fail, the
   finding is refuted: reply with the evidence (the test you wrote, or the
   invariant in `AGENTS.md`/`CLAUDE.md` that already covers it) and change
   nothing.
2. **Reply on the thread** with `fixed in <sha>` + the test name, or
   `refuted:` + the reason. Then `resolve_review_thread(threadId)`.
3. A P0 on data loss or auth is fixed the same way, but the merge in step 6
   waits for the human.

Rules that make this one pass and not a loop:

- Never request a second full review. If a FIX is itself large (> ~100
  lines) or touches a path in the P0 list, one targeted re-check is allowed:
  `@codex review only the commits after <sha> for regressions in <area>`.
  That is the only exception.
- Do not "address" a finding by weakening a test, widening an exception
  handler, or adding a `noqa`/`type: ignore` — those are refutations in
  disguise and get refuted for real in the next audit.
- Do not fix things Codex did not raise unless they block the fix; scope
  creep here is how one pass becomes three.

Push the fixes as one or a few commits with `review:` prefixes (they vanish
in the squash; the reply threads keep the record). Fill in the PR body's
"Codex review outcome" line.

## 5. Wait for green

CI must be green on the fix commit (both Python legs). If it is red, that is
this PR's problem: fix and push; never re-run to "see if it passes".

## 6. Merge

- `merge_pull_request(merge_method="squash", commit_title="<PR title> (#N)",
  commit_message=<the PR body's Why + What changed, verbatim>)` — never the
  concatenated commit list.
- Delete the branch (repo setting "automatically delete head branches", else
  `git push origin --delete <branch>`); `unsubscribe_pr_activity`; close the
  linked issue with a one-line comment if the PR body did not `Fixes #`.
- Report to the user: PR link, findings/fixed/refuted counts, merged sha.

## Stop and ask when

- Codex raised a P0 on `auth.py`, `http_admin.py`, session files, migrations
  or anything that can lose data — fix, then the human merges.
- Two findings contradict each other or a rule in `AGENTS.md` — the rule may
  be wrong; that is a decision, not a fix.
- The fix pass would exceed the PR's own size.
