# Assessment recording

Why this exists: ADR 0006 decision 5 decides that the server stores the
COMPONENTS of a game-quality verdict rather than a score; this file carries the
implementation notes — the declared-only provenance rule, the exact-or-mint
write path (issue #150), the same-day replace index, the void repair, every read
path that surfaces a verdict, and the hard constraint that none of it ever
touches affinity or discovery. Moved out of the root `CLAUDE.md` on 2026-09-01.

## Assessment recording (ADR 0006 decision 5)

**Assessment recording** (ADR 0006 decision 5): `record_assessment` (a MUTATION tool of its own, never folded into `get_assessment_context` — a merged tool inherits the strictest annotation — nor into `rate_game`, which feeds affinity) stores the COMPONENTS of a game-quality verdict, not a score: verdict, one-line summary, craft numbers, fit call, anchors cited, flags, price seen/target, `instead_game_id`, `context`, plus ownership/wishlist state AT THE TIME — and, since issue #153, the METHODOLOGY that produced it (`skill`, `skill_version`, `model`). Those three are **declared-only claims, NULL = unknown**: the server never default-stamps its own canonical skill version or a model name, because a stale installed skill copy or an ad-hoc assessment must not inherit the server's idea of "current", and lightly normalized only (strip, lowercase skill/model, version case preserved, over-cap rejected). History is append-only with ≤1 row per (game, UTC day) — a same-day re-record REPLACES that day's row through the `(game_id, date(assessed_at))` expression index, mirroring play_history's convention. An unknown candidate gets a games row minted through the sync_wishlist mint path (anti-collapse guards included), and the Steam appid rides on the assessment row because an unowned candidate has no `game_platforms` row to carry an identifier; that ownership-free row is a THIRD legitimate bare shape, exempted from `detect_orphan_games`' orphans as `assessment_only_count`. **Write paths never resolve a name loosely** (issue #150): `record_assessment`'s name branch is exact-or-mint, exactly like `add_game_to_platform`, because the failure modes are not symmetric — a fuzzy write filed an "Alan Wake 2" verdict onto the library's "Alan Wake" with `created: false`, which nothing surfaces, while a typo that mints a phantom row is visible and `merge_games`-repairable. Tiered/fuzzy matching survives only on the read path (`get_assessment_context`), where a trailing-ordinal guard turns a sequel-shaped near miss into `not_found` + `resolution.rejected_near_miss`, and both tools report a `resolution` block (mode/query/matched_name) so the caller can diff the row actually used against the candidate it meant. A misfile noticed after the same-day replace window is repaired by `void_assessment(assessment_id=…)` — its own NON_IDEMPOTENT_MUTATION tool rather than a mode, since a hard delete is not idempotent and a merged tool inherits the strictest annotation; it HARD-deletes that one row (a verdict about the wrong game was never an observation, so tombstoning it would only keep it in calibration) and suggests `delete_game` when the void leaves a minted row bare. Read paths: `get_game_detail` (single mode) and `get_assessment_context` carry the 5 newest verdicts (with true total + truncation flag), `get_wishlist`/`get_wishlist(with_prices=True)` annotate each item with the latest verdict and target price (`below_assessed_target` when the best SAME-CURRENCY price reaches it), `get_stats(report="assessments")` browses, and `get_stats(report="calibration")` compares verdicts against what was actually acquired/played/rated (per-currency money, capped mismatch lists, NULL `last_played` counted as unknown) and regroups the same deduped rows by declared provenance in `by_methodology` (per skill+version) and `by_model` — both capped with count/truncated, both keeping the NULL bucket with explicit nulls, since unversioned history is still history. The wishlist/deal annotation deliberately does NOT carry provenance — a deal doesn't need it. **Hard constraint: verdicts never feed `tag_affinity` or `discover_games`** — no recompute (not even the deferred one every other bulk write does), no ranking join. Recording never writes the wishlist either: a `wishlist_for_sale` verdict on an unwishlisted game answers with a `suggested_action` naming `add_game_to_platform(..., wishlist_source="assessment")`. Since the evaluation card (apps_eval.py), a single-mode non-void `record_assessment` response also assembles a best-effort `package` block for the card — media via `data/media.py` (Steam appdetails screenshots/movies with constructed legacy mp4s HEAD-gated, IGDB screenshots/YouTube ids/similar-games, meta-KV cached, stale-served on failure; similar games are IGDB-only and get borrowed onto Steam-sourced results), anchors/comparisons/similar/pedigree (studio + previous games + library track record) annotated against the library — wrapped so assembly can NEVER fail or outlast the write (`_safe_package`, 10s budget); the batch mode returns no package.
