# ADR 0005: MCP 2026-07-28 readiness — track stable SDKs, stay stateless at the app layer

Status: accepted (2026-07-27)

## Context

- The MCP specification revision **2026-07-28** finalizes the day after this
  ADR. Its changes, from the published changelog (RC locked 2026-05-21):
  - **Stateless core** (SEP-2567/2575): the `initialize`/`initialized`
    handshake and `Mcp-Session-Id` are removed; protocol version, client
    info, and capabilities ride `_meta` on every request; a mandatory
    `server/discover` RPC advertises server identity/capabilities. List
    endpoints must not vary per-connection. Cross-call state must be
    explicit, server-minted handles passed as ordinary tool arguments.
  - **Transport**: `Mcp-Method`/`Mcp-Name` headers required on Streamable
    HTTP POSTs; SSE resumability (`Last-Event-ID`) removed; the HTTP GET
    stream and `resources/subscribe` are replaced by `subscriptions/listen`.
  - **MRTR** (SEP-2322): server-initiated requests (sampling, elicitation,
    roots) are replaced by `InputRequiredResult` + client retry; every result
    carries a required `resultType`.
  - **Tasks** (SEP-2663): the 2025-11-25 *experimental* tasks are redesigned
    as an official extension (`io.modelcontextprotocol/tasks`) — polling via
    `tasks/get`, no `tasks/list`, unsolicited task handles allowed.
  - **Caching** (SEP-2549): `ttlMs` + `cacheScope` required on `tools/list`,
    `prompts/list`, `resources/list`, `resources/read`,
    `resources/templates/list`; tools SHOULD come back in deterministic
    order.
  - **Deprecated** (12-month window, new implementations should not adopt):
    Roots, Sampling, **Logging** (`notifications/message` — migrate to
    stderr/OTel), HTTP+SSE transport, RFC 7591 DCR (in favor of Client ID
    Metadata Documents).
  - Resource-not-found error code changes `-32002` → `-32602`; MCP Apps
    becomes first-class; tool schemas loosen to full JSON Schema 2020-12.
- SDK reality on release eve: the official Python SDK's v2 is at 2.0.0rc1
  (released 2026-07-27); **FastMCP stable is 3.4.4** (protocol 2025-11-25),
  with 4.0.0 only at alpha (a2). Both registered clients of this deployment
  (claude.ai and chatgpt.com — the ADR 0004 differential probe) speak
  current revisions; neither advertises 2026-07-28 yet.
- An audit of this codebase against the new revision found it already
  conforms everywhere the *application* (not the SDK) is responsible:
  - **No per-connection state.** The library is global single-user state
    (ADR 0001); `sync(targets=["library"])` returns an immediate ack polled
    via `get_sync_status` — exactly the explicit-handle/polling shape the
    redesigned tasks extension standardizes. The session-ingest nonce is an
    HTTP artifact, not MCP session state. `tools/list` never varies
    per-connection, and registration order (module order in `main.py`) is
    deterministic — the new SHOULD is satisfied.
  - **No deprecated features beyond logging.** Roots and sampling are
    unused. `tools/common.py::info` sends `ctx.info` logging notifications
    from the sync paths — deprecated in the new revision, fine in the
    current one; server-side `logging`-module output to stderr already
    exists in parallel.
  - **No custom error codes.** Nothing emits `-32002` or anything in the
    newly reserved `-32020`..`-32099` range.
  - **The duplicate-text opt-out survives.** The draft *keeps* the
    "SHOULD also return the serialized JSON in a TextContent block" clause,
    so `response_encoding.py`'s measured, per-deployment opt-out (ADR 0004)
    is unchanged in status: still a deliberate deviation from a SHOULD,
    still env-revertable.
  - **Auth hardening is mostly client-side MUSTs** (iss validation,
    `application_type`, credential-issuer binding); the server side arrives
    with SDK upgrades.

## Decision

1. **Track the latest stable SDKs; do not ship pre-release SDKs to prod.**
   Stay on fastmcp 3.x + mcp 1.x (bumped to 1.28.1 with this ADR), protocol
   2025-11-25. Adopt the 2026-07-28 revision when BOTH: FastMCP 4 (or mcp
   SDK v2) is stable, and a registered client advertises the new revision.
   The stateless transport, `Mcp-Method`/`Mcp-Name` headers, `resultType`,
   `server/discover`, and `ttlMs`/`cacheScope` emission all live in the SDK
   layer and arrive with that upgrade, not before.
2. **Use the current revision fully at the app layer.** Added with this ADR:
   server identity metadata (`version`, `website_url`, and a data-URI icon
   on the `FastMCP` instance — self-contained by the same no-CDN rule as the
   apps widget), and the complete annotation vocabulary
   (`destructiveHint=True` made explicit on the destroy-prior-state tools;
   `create_session_ingest_link` split onto a non-destructive `MINT_TOOL`
   annotation since minting never invalidates anything). Already in place
   before this ADR: tool titles, read-only/idempotent/open-world hints,
   structured output with typed response models, progress notifications,
   server instructions, and MCP Apps.
3. **App-layer statelessness is now a rule, not a coincidence.** No new tool
   may depend on per-connection state or vary `tools/list` per-connection;
   cross-call state uses explicit arguments/handles (the `sync` ack +
   `get_sync_status` pattern). This is what makes the eventual SDK bump a
   dependency upgrade instead of a redesign.
4. **Migration checklist for the actual revision bump** (a future PR, in
   order):
   - Bump to stable FastMCP 4 / mcp v2; the transport statelessness,
     required headers, `resultType`, `server/discover`, and cache metadata
     come from the SDK. Choose real `ttlMs`/`cacheScope` values then
     (`tools/list` is stable per deploy → long TTL; single-user → private).
   - Drop the `ctx.info` notifications in `tools/admin.py` sync paths
     (logging is deprecated; stderr logging already covers it). Progress
     notifications survive — they are request-scoped, not the logging
     feature.
   - Map `sync`'s fire-and-forget onto the tasks extension
     (`io.modelcontextprotocol/tasks`) if the SDK exposes it; keep
     `get_sync_status` during the transition — clients on the old revision
     still poll it.
   - Revisit `apps.py`: the hand-rolled bridge pins
     `ui/initialize` `protocolVersion: "2026-01-26"`; update when hosts
     advertise the first-class Apps revision (watch for renamed methods).
   - Re-run the ADR 0004 differential probe before assuming either client's
     `structuredContent` behavior carried over to its new-revision stack.
   - Confirm the OAuth provider (FastMCP GitHub provider) emits RFC 9207
     `iss` and supports Client ID Metadata Documents; DCR stays as fallback.

## Rejected (and why)

- **fastmcp 4.0.0a2 / mcp 2.0.0rc1 now** — alpha/rc APIs on a production
  server, for a revision no registered client speaks yet. The Python SDK's
  own beta notes say public APIs may still change.
- **Hand-emitting `ttlMs`/`cacheScope` or `Mcp-*` headers from middleware
  ahead of SDK support** — unknown result fields risk being stripped or
  rejected by 2025-11-25 validators, and the only clients that would read
  them are new-revision clients, which require the new SDK anyway.
- **Adopting the 2025-11-25 *experimental* tasks (`task=` in fastmcp 3.x)
  for `sync`** — the 2026-07-28 revision redesigns that lifecycle
  incompatibly (`tasks/result` → `tasks/get` polling, `tasks/list`
  removed), and no registered client drives experimental tasks. The
  hand-rolled ack+poll works on every client today and is already shaped
  like the final design.
- **Adopting elicitation for the `delete_game`/`confirm` flow** — the
  server-initiated form is replaced by MRTR in the new revision; the
  two-step `confirm` parameter works identically on every client and
  revision.
- **Tool-level icons on all 29 tools** — connect-time bytes for decoration
  hosts barely render; the server icon covers identity.

## Consequences

### Positive
- Today's clients see complete server identity and honest, complete
  annotation hints; nothing about the wire surface waits on the new spec.
- The revision bump is pre-scoped: a dependency upgrade plus the four
  code-level items in the checklist, instead of an open-ended redesign.
- `mcp` is current within 1.x (1.28.1).

### Negative
- The server does not speak 2026-07-28 on release day. Accepted: neither
  do its clients, and the deprecation window for everything it uses is
  12+ months.
- The `MINT_TOOL`/`NON_IDEMPOTENT_MUTATION_TOOL` split is one more
  annotation constant to keep honest (ADR 0004's strictest-annotation rule
  still applies to any future merge).
